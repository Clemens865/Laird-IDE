# Laird — Theming engine and non-functional requirements

Part of the technical PRD. See `docs/prd/README.md` for the full index.

## Theming engine

Treat the design directions explored in `design/variations/` (v1–v9, with v9-signature now locked as the default) as the first drafts of a **token contract**, not disposable mockups: surface colors, ink colors, radii, shadow/elevation, font stack (display/body/mono), and a motion-signature slot (e.g. v5/v9's drifting mist, the board-flip) — all as CSS custom properties / a theme object that every UI component consumes, never hardcoded colors in component code. This makes switching themes later a token-swap, not a rewrite, and directly reuses the work already done rather than treating it as throwaway.

**Built, retrofitted, and live-verified (Workstream F).** `tokens.css` carries every category below for real; `v9.css`'s own glass/shadow effects — hardcoded to literal `rgba(255,255,255,…)`/`rgba(27,39,48,…)` before this workstream — were retrofitted to two RGB-triple tokens (`--surface-rgb`/`--ink-rgb`) so a theme can actually repaint them, not just the named surface/ink tokens a theme would naturally think to redefine. A complete second theme (`midnight.css`, a dark theme, pure token overrides, zero component changes) proves this for real, toggle-able from the UI and confirmed with real before/after screenshots. **A major, previously-invisible bug was found and fixed getting here**: `v9.css` had never actually been imported into the running app since it was first written — every prior workstream's UI had been rendering unstyled the entire time, undetected because all verification until now was DOM-structure-based, never a real screenshot. Fixed with one import line; the plan's own notes record this as the most important lesson of the workstream — real screenshots now belong in the standard verification loop for UI-facing work, not just this one.

**Concrete category list, validated against `docs/research/external-analysis/bhil-helm-sci-fi-visualizer.md`'s independently-built token schema** (same shape, different values — good external confirmation this is the right set of categories, not sci-fi-specific): background tiers (surface / sunk / raised), text tiers (ink / ink-2 / ink-3), one accent pair per theme, **four semantic alert states** (info / success / warning / danger — not yet in any current mockup, which only has decorative per-project accent colors; needed once real status, not just project identity, needs a color), one glow/highlight token, font slots (display / body / mono — v9 already has this: Newsreader / Inter / JetBrains Mono), a spacing scale, and motion durations with an explicit `prefers-reduced-motion` override block (the concrete schema home for the motion-safety requirement below).

**License note carried over from design research**: do not vendor React Bits / Canvas UI component source (MIT + Commons Clause — fine to use the *technique*, risky to resell a product substantially built on their literal code) or any xyz palette sourced from `nice-color-palettes` (CC BY-NC-SA, non-commercial only). Every effect in the mockups was hand-rolled in plain CSS/SVG specifically to avoid this — keep doing that as the theme engine is built out.

## Non-functional requirements

- **Performance budget**: multiple concurrent Claude Code sessions (one process tree per active project tab) must not degrade UI responsiveness. Adopt the same discipline xyz's own engineering guardrails use (good practice regardless of that project's licensing): cap simultaneous heavy visual effects (glass/blur/animated backgrounds) to a small number active at once, pause/simplify effects for background (non-focused) project tabs.
- **Motion safety**: no flashing above 3Hz, a reduced-motion fallback for every animated element (mist drift, grain, the board-flip), consistent with WCAG 2.3.1.
- **Accessibility**: real semantic elements (buttons, inputs, labels) under every styled surface, 4.5:1 text contrast minimum per theme (checked per theme at token-definition time, not per component). **Currently thin for an explicitly non-engineer-facing product** — still missing: keyboard navigation for tab/grid switching, ARIA live-region behavior for the streaming activity feed (it updates continuously like a chat, not a static page), and any i18n/localization stance. Needs a real pass, not just the contrast/semantics baseline above.
- **Security**: see `observability-trust-and-harness.md` for the concrete trust/guardrail mechanism (tiered permissions, kill switch, plan-bound confirmations) — this used to be a single sentence here with no mechanism behind it.
- **Offline/local-first**: no required cloud dependency for core usage (session running, skills, observability). Plugin marketplace installs need network; everything else should work offline.
- **Telemetry**: no stated position yet. Worth being explicit — either "Laird collects no usage telemetry" or "opt-in only" — rather than silent, given how much the product PRD leans on a privacy/local-first trust message elsewhere.
- **Distribution**: no stated position yet on auto-update or macOS code signing/notarization. A real pre-launch requirement with no coverage so far.
