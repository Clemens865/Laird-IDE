# Laird — Observability, trust & guardrails, and harness mode

Part of the technical PRD. See `docs/prd/README.md` for the full index.

These three were originally separate sections, but they all read from and write to the same place — `ActivityLogEntry` (see `architecture-and-data.md`) — so they're kept together here rather than split across files that would just cross-reference each other constantly.

## Observability layer

Claude Code already reports token usage and cost per turn/session. Laird's job is translation, not instrumentation:

- Per-session plain-language footer: cost, elapsed time, files changed (already in the mockups). **Built** (`CostFooter.tsx`, Workstream A).
- Per-project history: a simple local timeline of past sessions, their cost, and outcome — enough for a non-engineer to answer "what has this agent been doing and what did it cost me" without reading logs. **Built and live-verified** (`src/main/session/history.ts` + `SessionHistoryView.tsx`, Workstream D). Outcome is reported honestly as `running`/`completed`/`needs review` (mapped from the real `Session.status`) rather than the originally-drafted "shipped / abandoned / needs review" — Laird has no actual signal yet to distinguish "shipped" from merely "completed," since that judgment is harness mode's job (below), not this surface's.
- No separate observability SaaS (Langfuse/Braintrust-style) integration planned for v1 — the whole point is this lives inside the workspace, in plain language, per the product PRD's gap analysis. A future "export to Langfuse" could be a plugin, not core.

**Researched against the real 2026 LLM-observability landscape** (`docs/research/observability-landscape-2026.md` — OpenTelemetry's GenAI semantic conventions, OpenInference/Phoenix, Traceloop/OpenLLMetry, Langfuse, Braintrust, LangSmith, Helicone). This reaffirms the "no SaaS for v1" line above rather than reversing it — OTel's wire protocol, collectors, and auto-instrumentation agents solve cross-service distributed tracing and SDK-call-site monkey-patching, neither of which Laird has (it's one local desktop process shelling out to the real `claude` CLI and parsing real NDJSON itself — that parser, `mapEvents.ts`, already *is* Laird's instrumentation layer). What *is* worth adopting now, while the schema is still small and cheap to change, is vocabulary alignment at the field-naming level, so a future export plugin is a field copy rather than a lossy reconstruction:

- **`UsageEvent` currently discards real data it already receives.** The real `claude` CLI's result line reports `input_tokens`/`output_tokens`/`cache_creation_input_tokens`/`cache_read_input_tokens` on every turn (confirmed live back in the Foundation workstream's own spike) — `UsageEvent` today only persists `costUsd`/`durationMs`/`filesChanged`. **Built**: added `inputTokens`/`outputTokens` (named to match OTel GenAI's `gen_ai.usage.input_tokens`/`output_tokens` directly) plus `cacheReadTokens`/`cacheCreationTokens` (Laird-specific — OTel GenAI doesn't yet standardize cache tokens as of 2026).
- **Laird's existing `Session` → `Turn`/`ActivityLogEntry.turnId` → individual `ActivityLogEntry` rows hierarchy already cleanly matches OpenInference's session → trace → span model** — confirmed, not redesigned. Worth stating explicitly so a future contributor doesn't "fix" this into unneeded complexity thinking it's unprincipled.
- **`Subagent` gets an explicit parent link**, matching OpenInference's "a child span inherits its parent agent's id" rule. **Built**: `Subagent.parentActivityLogEntryId`, pointing at the `ActivityLogEntry` row for the `Agent` tool-call that spawned it — today a subagent was only correlated to its session by `sessionId` + Claude Code's own `task_id`, with no queryable record of *which* turn actually spawned it. This is also directly load-bearing for harness mode's evidence-tier lineage (below): a `VERIFIED` claim backed by "a subagent checked this" needs an explicit, queryable lineage, not inferred stream-order proximity.
- **`ActivityLogKind` keeps its own small vocabulary rather than adopting OpenInference's full 10-span-kind taxonomy or Langfuse's `EVENT`/`SPAN`/`GENERATION` split wholesale** — both are heavier than what Laird's event stream actually produces (no embeddings/retrieval/reranking/guardrail-model spans to separate out). Where a real overlap exists, the *mapping* is worth knowing even without a literal rename: `'tool-call'` ≈ `execute_tool`, a `Subagent` spawn ≈ `invoke_agent`, a `Turn`'s text response ≈ `chat`. `'kill-switch'`/`'permission-prompt'` have no standard-vocabulary equivalent at all — they're Laird's own trust mechanism, not a telemetry concept — and stay exactly as Laird-specific, unprefixed, for now. Traceloop/OpenLLMetry's own pattern (extend `gen_ai.*` with vendor-prefixed attributes rather than fork the vocabulary — `traceloop.span.kind`, `traceloop.workflow.name`) is the right model to copy *if* an export plugin is ever built, reserving a `laird.*` prefix for that day rather than guessing at it now.
- **No equivalent of Laird's own evidence-tier model exists anywhere in the mainstream landscape surveyed** (OTel GenAI, OpenInference, Langfuse, Traceloop, Braintrust, LangSmith, Helicone) — confirmed as genuine Laird-specific differentiation (a *trust-tier* concept — how do I know this claim is true — not a *telemetry* concept — what happened, what did it cost), not a gap to fill from outside.

**Two rules added from `docs/research/external-analysis/bhil-helm-sci-fi-visualizer.md`**, load-bearing for every observability surface, not just harness mode:

- **Decorative-vs-signal labeling.** Anything in the activity stream, sidebar, or theme (ambient mist drift, grain texture, the board-flip animation itself) is illustrative, not a fact about what the agent did — it must be structurally distinguishable from real status (tab state text, the flip's active/idle meaning, file-change chips), never visually conflatable with it. This is what keeps the "never feels like a terminal, but never lies either" promise honest as the theming system (`design-system-and-nfr.md`) grows more atmospheric.
- **Evidence-tier labels on agent self-reported claims.** When a turn says "tests passed" or "file updated," that claim should carry a tag — `VERIFIED` (Laird itself re-ran/confirmed it), `CORROBORATED` (confirmed by a second, independent source), `UNCORROBORATED` / `INFERENCE` / `STATED` (the agent said so, unchecked) — rather than being rendered as flat fact. Backed by the `ActivityLogEntry` table: a `VERIFIED` tag should point at the log entry that proves it.

## Trust & guardrails

This was previously a single sentence under "non-functional requirements" with no real mechanism behind it. **Concrete mechanism added from `docs/research/external-analysis/ruvnet-github.md` (its single most directly reusable finding) and `convidence-ai.md`, now built and live-verified against real, billed `claude` sessions (Workstream D):**

- **Tiered permission × approval mode.** Each project has a permission tier — `read` / `write` / `manage` / `full` — crossed with an approval mode — `ask` / `auto`. Mapped onto Claude Code's real tool surface in `src/main/session/permissions.ts`: `read` is Read/Glob/Grep only; `write` adds file edits; `manage` adds subagents/skills/web research; `full` adds a scoped, denylisted `Bash` (the only tier with shell access at all). Each tier is strictly additive over the one below. Defaults to `write`/`auto` — matches the product's pre-Workstream-D implicit behavior, so nothing changes for an existing project until a user explicitly dials it up or down. Surfaced as an always-visible selector (`PermissionControl.tsx`), never buried in a settings menu.
- **Hard exceptions regardless of tier or mode — implemented as a flat denylist, not a confirmation gate, and here's why.** The PRD's original wording called for destructive/spend/network actions to "always require an explicit confirmation, even in `auto` mode." Building this surfaced a real architectural constraint: a headless `claude -p` session has no human attached mid-turn — there is no TTY, no mechanism to pause and resume on an answer. The honest, stronger substitute actually shipped: `FULL_DISALLOWED` commands (`sudo`, `rm -rf`, `git push --force`, `git reset --hard`, `git clean -f`, etc.) are never allowed at all, in any tier or mode — enforced by Claude Code's own `--disallowedTools`, confirmed live (a real agent at the `full` tier, told to run `rm -rf` on a real file, was genuinely refused by the real CLI; the file survived; the agent's own text response reported the refusal). Spend itself needs no extra gate by construction — a session only ever starts from an explicit human "send," itself optionally gated by the plan-bound confirmation below.
- **Plan-bound confirmation.** A confirmation is bound to the *specific* proposed action (lightweight version of Convidence_AI's plan-hash idea): in `ask` mode, sending doesn't start a session — `SessionManager.requestStart` returns a pending confirmation keyed to the exact prompt text, and `confirmStart` rejects it outright if the text doesn't match or it's already been consumed, rather than silently re-running a stale approval. Live-verified: the confirmation shown is provably the confirmation that runs, cancelling starts nothing and leaves no trace, and the real session afterward produces exactly what was confirmed.
- **A live, always-visible action log** — the UI rendering of the `ActivityLogEntry` table (`ActionLog.tsx`), not a separate feature. Built, pushed live from `sessionManager.ts`'s one write path, and rendered in plain language (never a raw payload dump) — verified with real entries from a real session.
- **A one-click "Take back control" kill switch.** Immediately stops the real process (`SessionManager.killSession`, the same kill mechanism Workstream A's hardening pass already proved against a real OS process table) and revokes the *project's* autonomy — Laird's one-process-per-turn architecture has no "next action" inside an already-dead process to refuse, so the real next action that gets refused is starting a fresh session, until `grantAutonomy` explicitly re-arms it (`AutonomyRevokedBanner.tsx` replaces the composer entirely in the meantime). Always visible while a session is running, never buried in a menu. Live-verified end to end: real process confirmed killed via the real OS process table, a new session genuinely refused until resumed, and a real session afterward working again once resumed.
- **Honest disclosure for the plugin marketplace** (`skills-and-plugins.md`): state plainly that installed plugins run with the user's full account permissions and are not sandboxed — borrow ruflo's own wording pattern, not just a vague "review before installing" footnote. Not yet built — Workstream E's job.

The baseline security requirement this replaces: never bypass Claude Code's own permission/confirmation system for destructive actions; surface permission prompts as native Laird UI (not a raw terminal prompt) but with identical semantics; one writer per worktree, consistent with this project's own stated concurrency rules.

## Harness mode (reworked twice — converged on a concrete model, then hardened against a real field-tested blind spot, still needs a visual design pass)

**Status change**: this was flagged as the least-specified, least-validated pillar in the original draft. Two independent research hits — `bhil-helm-sci-fi-visualizer.md` (primary) and `convidence-ai.md` (secondary, via its plan/evidence pattern) — converged on the same architecture, so this is no longer a from-scratch design problem, just an implementation one. Note on naming: `metaharness.md` turned up a false cognate — that project's "harness" means a repo-scoped agent *scaffold*, unrelated to this eval/test-harness meaning; its findings landed in `skills-and-plugins.md`, not here.

**Second research pass, against the broader 2026 AI-agent eval-harness field** (`docs/research/harness-engineering-landscape-2026.md` — OpenAI Evals, Anthropic's own `claude plugin eval`, the UK AISI's Inspect, Braintrust, promptfoo, DeepEval, LangSmith evals, W&B Weave, SWE-bench, and visual-regression tooling), prompted directly by a real blind spot this project found in itself (Workstream F's `v9.css` bug: code/DOM-level checks all passed while the actual rendered UI was broken the whole time — the harness's own reviewer has exactly the same blind spot unless hardened against it on purpose). **The single most important finding**: `claude plugin eval` — confirmed real and already installed on this machine — is a genuine eval-harness mechanism built into Claude Code itself, and architecturally more mature than this section's own prior draft. It can't be called directly (it evaluates a *plugin's* own prompt-triggering behavior, not a project's acceptance criteria), but every one of its mechanisms below is a direct, concrete fix for a real gap here, and reusing the *shape* keeps Laird consistent with its own standing philosophy of never reinventing a Claude Code mechanism that already exists.

A project has one or more **harness specs**: numbered, plain-language acceptance criteria ("1. the signup form should work on mobile," "2. the API should reject negative amounts") attached to a project. Running the harness invokes a dedicated **reviewer subagent** (already present in the mockups) against the converged model from `bhil-helm-sci-fi-visualizer.md`'s `helm-qa` pattern:

- **Fresh-context, never the builder.** The reviewer runs in its own context, separate from whatever session did the work, and only checks — it never fixes anything itself. This is what makes its verdict trustworthy rather than a builder grading its own homework.
- **The reviewer must be a different model than the builder, at minimum a different size.** Field-validated addition: "using the judge and the agent from the same model family introduces correlated error — the judge shares the same blind spots as the agent" (2026 LLM-as-judge consensus, DeepEval's field guide among others). Fully compatible with Laird's single-provider-v1 non-goal (a different Claude model size, not a different provider) — an explicit harness-mode setting, not left implicit the way `claude plugin eval`'s own `--judge-model` (default haiku, distinct from whatever model did the work) already treats it.
- **A decisive disposition, not a vague pass/fail — now four outcomes, not three.** The harness run reports **SHIP / HOLD / REWORK**, plus a new **UNVERIFIABLE** (the criterion itself is ambiguous or impossible to check as written — a property of the *criterion*, not the agent's work), against each numbered criterion, backed by the `ActivityLogEntry` table — "did the agent touch `Settings.tsx`" is a log query, not a re-derived guess. `UNVERIFIABLE` is directly motivated by a real 2026 cautionary tale found in this same research pass: OpenAI's own Frontier Evals team stopped reporting SWE-bench scores after an internal audit found over 60% of a sampled "resolved" set were actually unsolvable as written, because the *tests* were flawed, not the agents. Laird's own criteria are written in plain language by a non-engineer user — a strictly harder authoring problem than SWE-bench's (which still got the majority wrong with professional maintainers writing the tests) — so "I can't tell what this means well enough to check it" has to be a real, surfaced outcome, never silently guessed past.
- **Multi-run aggregation, not a single reviewer pass.** A single LLM-graded run is field-recognized as unreliable on its own; `claude plugin eval` defaults to 3 runs per case for exactly this reason. Laird's own reviewer invocation should default to the same, not a one-shot check.
- **An ablation/baseline comparison where feasible** — `claude plugin eval`'s own default behavior: run a "before this change" baseline alongside the real result and report the *delta*, isolating "did this pass because of the agent's work" from "would this have passed anyway." Makes a `VERIFIED` tag meaningfully stronger than a post-hoc check alone.
- **Mock-first, real-opt-in for anything with external dependencies (MCP servers, network calls)** — again `claude plugin eval`'s own default: a dependency with no mock simply isn't started, keeping most runs fast/deterministic/free; real servers only start with explicit opt-in. The same "explicit, never ambient" discipline already governing Laird's own skill/MCP materialization (`skills-and-plugins.md`), applied here too.
- **A cost ceiling per run**, matching `claude plugin eval`'s own `--max-cost-usd` — a harness run should be boundable the same way a CI pipeline is cost/time-gated, not open-ended.
- **Evidence tiers on every claim** (above) — each criterion's result carries VERIFIED/CORROBORATED/UNCORROBORATED/INFERENCE/STATED, so "I checked this" and "the agent said this" are never visually the same thing.
- **No silent correction.** Gaps or contradictions the reviewer finds surface in the harness result, not quietly patched by the reviewer itself — keeps the harness a check, not a second builder.

Still modeled after Braintrust's natural-language-scorer spirit (a human writes criteria in English, an agent checks them) but now with a concrete output shape and a concrete process boundary (fresh context, check-only) instead of an undefined "pass/fail." **Machine-checkable sub-checks vs. pure LLM judgment — now a real answer, not just an open question.** SWE-bench's own mechanism is the strong, concrete answer for any criterion that reduces to "the tests should pass": run the project's actual test command in its own environment and query the real exit code — no LLM judgment needed at all, and `bhil-helm-sci-fi-visualizer.md`'s `tools/contrast.py`/`validate.py` (stdlib-only Python validators) remain a worth-a-look minimal example of the same idea for narrower, bespoke checks. Reserve LLM judgment for criteria that are genuinely qualitative (no deterministic test can check "looks professional").

**DeepEval's agent-trajectory metric categories — task completion, step efficiency, plan adherence, plan quality — are a useful vocabulary for criteria about *how* the agent worked, not just whether the end state looks right.** Worth adopting as a naming scheme, not the library itself: every one of these is computable directly from Laird's own existing `ActivityLogEntry` log (did the agent touch the files it claimed to, how many turns/tool-calls did it take, did it follow a stated plan) with no new data collection needed.

**Visual evidence, not just code inspection — user-proposed, feasibility confirmed live.** The exact gap Workstream F's own `v9.css` bug exposed (code-level/DOM checks can all pass while the actual rendered UI is broken or never seen) applies just as much to the harness's own reviewer: a criterion like "the signup form should work on mobile" cannot honestly reach `VERIFIED` from reading source code alone. Confirmed live: the headless `claude -p` reviewer subagent, given only `Read` tool access, can genuinely see and correctly describe a real screenshot image passed as a local file path in its prompt (not merely infer from a filename) — so a harness run can drive a real Playwright browser against the target project's own running UI, save a real screenshot, and hand that screenshot to the reviewer as the evidence backing a `VERIFIED` tier on a UI-shaped criterion, exactly parallel to how `ActivityLogEntry` backs a `VERIFIED` tier on a code/action-shaped one.

**Not every UI criterion should go through an LLM judge, though — baseline-diffing is the industry default, zero-shot visual judgment is the narrower special case.** Real finding from the second research pass: Percy, Chromatic, and Playwright's own built-in screenshot comparison are all *baseline-diff* tools first — they compare a new screenshot against a previously-*accepted* one, using perceptual-diff math only to separate a genuine regression from noise (anti-aliasing, font hinting), never judging a screenshot cold. Laird's harness should split the same way: "the button should still look the way it did before this change" is a baseline-diff question — cheap, deterministic, no LLM needed once a baseline screenshot exists. "The signup form should look professional on mobile" is a genuinely novel qualitative judgment with no baseline to diff against, and is the real, narrower case where the screenshot-to-reviewer approach above actually earns its cost. Which mechanism a given criterion needs is a property of the criterion, decided once when the spec is written, not re-decided every run. **Open ownership question**: the LLM-judged half above is designed and live-verified; the deterministic local pixel-diff half has no owner yet.

**Open design question this still needs, before implementation**: how a harness run knows how to reach a project's own UI to screenshot it at all — projects vary (a web app with a dev server and port, a native app, a CLI with no UI, nothing running yet). Recommended default, consistent with the precedent already set by `skills-and-plugins.md`'s auto-recommend feature (cheap, read-only stack detection → an explicit, editable, user-confirmed proposal, never a silent auto-action): detect a likely dev/start command and default port from the project's own `package.json`/framework signature, show it to the user as a proposed, editable "how should Laird preview this project's UI" setting the first time a harness spec includes a UI-shaped criterion, and never launch anything without that explicit, visible configuration already in place.

**Interactive click-through, not just a static screenshot — also user-proposed, also feasibility-confirmed live, with one real constraint found.** A real, official Playwright MCP plugin (`playwright@claude-plugins-official`, already installed and enabled on this machine, bundling `npx @playwright/mcp@latest`) gives any Claude Code session genuine interactive browser tools — navigate, click, type, read element state — not just a one-shot screenshot. Confirmed live: a headless `claude -p` session, given only that MCP server's tools, genuinely drove a real browser against a real local page and reported back state that only exists after real multi-step interaction (a click-counter plus a fresh random token generated client-side on each click — unobtainable by reading the page's static source). This means a harness criterion like "clicking login should navigate to the dashboard" can be checked by the reviewer actually doing it, not inferring it from code. **The one real constraint found doing this**: `@playwright/mcp`'s `browser_navigate` refuses a bare `file://` URL — it genuinely needs a real HTTP server to connect to. This sharpens the open design question right above it: the harness doesn't just need to know a project's dev command for a screenshot, it needs to actually *start that real dev server* before the reviewer's browser tools have anything to connect to at all — the same "detect a likely command, propose it, confirm explicitly" pattern applies, now clearly for a real running process, not merely a path to open.

A real, honest caveat surfaced during this same live check, worth recording rather than glossing over: in an earlier attempt (no browser tool involved, just a static screenshot image handed to the reviewer), the model answered a question about the image's content correctly *without ever looking at it* — it found a faster shortcut (reading a sibling text file) and took it. A reviewer that can take a shortcut around actually looking will sometimes take it. **This is exactly why the evidence-tier model above is load-bearing, not decorative**: a harness result must record *which* evidence path the reviewer actually took (screenshot read vs. browser tool invoked vs. inferred from source) as part of what backs its `VERIFIED` tag — a criterion marked `VERIFIED` by visual/interactive evidence needs that claim checkable against the real `ActivityLogEntry`/tool-call log of that specific reviewer run, not just trusted because the reviewer said so. The second research pass independently confirms this is a named, field-recognized failure mode (self-preference/shortcut-taking judges), not a one-off fluke of this particular test.

**Record once, replay deterministically — a pattern for turning a one-off LLM-driven click-through into a durable, free regression check.** Playwright's own 2026 "Test Agents" feature ships a planner → generator → healer pipeline: a planner writes a test plan from a prompt, a generator turns it into a real Playwright script, and a healer repairs that script over time as the page changes. Applied to Laird's own click-through evidence (above): the *first* harness run against a UI-shaped criterion is LLM-driven and exploratory — but a successful run's script can be saved and replayed directly on every *subsequent* run against that same criterion. Fast, free, fully deterministic, and it only falls back to the LLM-driven exploratory path again if the saved script actually breaks (the project's UI changed shape) — directly addressing the cost/reliability tension the "machine-checkable vs. LLM judgment" discussion above already names, specifically for the click-through case.

**A concrete shape for the harness's own, still-undesigned results view**: `claude plugin eval`'s self-contained HTML report (per-grader verdicts, optionally published to claude.ai) is a real precedent worth starting from rather than inventing a report format from nothing, when this moves from spec to the visual design pass the "Known gap" below still calls for.

**Extended once more, same session: an embedded, live, user-interactive PiP window inside Laird itself — not a separate floating browser.** Rather than the reviewer's Playwright MCP server launching its own, invisible-to-the-user browser process, Laird could instead: embed a real Electron `BrowserView`/`WebContentsView` pointed at the project's dev server as a literal panel inside its own window; expose that one specific view over the Chrome DevTools Protocol (Electron's standard `--remote-debugging-port` mechanism, the same one Puppeteer-against-Electron integrations already rely on); and point the harness's `playwright` MCP server at it via its own confirmed `--cdp-endpoint <endpoint>` flag instead of letting it launch a separate browser. The result is one single browser surface that is simultaneously what the user sees live inside Laird *and* the exact thing the reviewer is clicking through — not a screen-recording of a separate window, the same session.

**The real design question this adds, before building it**: that embedded view is interactive for the *human* too, so a harness run and a user click could contend for the same page at the same time. Needs an explicit ownership rule before implementation — consistent with the concurrency discipline already in `architecture-and-data.md` ("only the integration owner edits shared state," applied here to a shared browser view instead of a shared worktree): most likely, the embedded view becomes harness-owned and visibly locked to user input for the duration of an active run (mirroring the kill-switch's own "Take back control" framing — the user can always reclaim it), rather than silently allowing both to drive the same page at once.

**What the second research pass explicitly says not to adopt**: any hosted/cloud eval SaaS as a v1 dependency (Braintrust's hosted UI, Percy/Chromatic's cloud diff services) — their *mechanisms* are worth the above, their hosted products aren't worth depending on, consistent with Laird's local-first non-goal; pairwise/swapped-position judging — a known bias-mitigation technique that doesn't map onto Laird's actual judgment shape (single-sided SHIP/HOLD/REWORK/UNVERIFIABLE dispositions, not A/B comparisons between two candidates); and a literal integration with `claude plugin eval` itself — it evaluates a plugin's own prompt-triggering, not a project's acceptance criteria, so the right move stays reusing its mechanisms, never calling the subcommand against a project.

**What's still genuinely unsolved, named honestly rather than assumed away**: no calibration process exists — in the field broadly, or in Laird's own design — for validating over time that a reviewer's `VERIFIED` judgments are actually trustworthy; the field itself names this as the single most under-invested mitigation, and Laird's own number here is currently zero. Exactly how "a different judge model size" should be surfaced as a user setting (silent default vs. an explicit per-project choice) is a product decision, not a technical one, and still open. And the deterministic local pixel-diff mechanism (the other half of the baseline-diff/LLM-judge split above) has no implementation owner yet.

**Known gap**: none of the nine design variations show a harness-mode screen — where criteria get written, or what a SHIP/HOLD/REWORK/UNVERIFIABLE result looks like on screen. This section is conceptually resolved; it has no visual design yet.
