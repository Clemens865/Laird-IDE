# Laird — Skills, subagents and the plugin system

Part of the technical PRD. See `docs/prd/README.md` for the full index.

Claude Code already has a real plugin ecosystem: slash commands, subagents, hooks, and MCP servers bundled via `.claude-plugin/marketplace.json`, installed with `/plugin install`, discoverable through decentralized git-based marketplaces (hundreds of first-party plugins, thousands of community ones as of 2026). Laird should **not** reinvent this — it should be a visual front-end over it:

- Read the user's installed plugins/skills/subagents directly from Claude Code's own config/marketplace state.
- Render them as the skill cards / collections view already mocked up (icon, description, shortcut, on/off).
- "Create a new skill" in the UI should generate a real Claude Code skill file (with guided prompts standing in for hand-writing YAML frontmatter + markdown), not a Laird-specific format. **Built and live-verified** (`src/main/skills/create.ts` + `CreateSkillForm.tsx`) — confirmed with a real `claude` session that a just-created, still-uncommitted skill is genuinely usable, not just visible in Laird's own UI; doing so also surfaced and fixed a real bug where an uncommitted project skill could be silently destroyed for a non-git project (see the implementation plan's Workstream C notes).
- Installing a community plugin should be a visual marketplace browser that shells out to the same mechanism `/plugin marketplace add` / `/plugin install` uses today, so anything installed through Laird also works in plain Claude Code and vice versa. **Built and live-verified** (Workstream E, `src/main/skills/marketplace.ts` + `MarketplaceView.tsx`) — scoped to marketplaces already configured on the machine; adding a brand-new custom marketplace from Laird's own UI, and the `ruflo` marketplace specifically, are deliberately backlogged (see `roadmap-and-open-questions.md`). Confirmed round-trip compatible with the real CLI: a plugin installed through Laird's UI shows up via `claude plugin list` exactly as if installed from the terminal, and vice versa.

This keeps Laird compatible with the existing ecosystem rather than fragmenting it — a real risk if Laird invents its own skill format.

## Three additions from research

From `docs/research/external-analysis/metaharness.md` and `ruvnet-github.md`:

- **Auto-recommend skills/subagents on first run, from repo analysis — built and live-verified (Workstream C, chunk 5).** Reuses the *idea* behind metaharness's "Repo → Harness" flow (analyze a project's file layout/stack, propose an editable starter set of skills/subagents) rather than this PRD's previous default of a blank "create a new skill" form — without reimplementing metaharness's own code or depending on its package; its scope (a Rust-kernel, 10-host-adapter factory) was always wildly oversized for the one feature Laird wants. What actually shipped: `src/main/skills/recommend.ts` scans a handful of real top-level files (tsconfig.json, package.json dependencies, requirements.txt/pyproject.toml, Cargo.toml, go.mod — read-only, never executed) for plain stack tags, then proposes already-discovered global skills whose own name/description substring-matches one of them — a `SuggestedSkills` banner in the Skills view, every suggestion pre-checked but individually uncheckable, shown only while a project has had zero sessions yet so it's a one-time first impression, not a recurring nag. Verified live end to end against this machine's own real global skill library, not just unit-tested.
- **A pre-flight "fit/cost" card before a session starts.** Two independent precedents converged on this: metaharness's `score <repo>` and ruflo's repo-analysis step both read a project (never execute it) and print a one-screen plain-language estimate — rough cost, what it's about to touch, obvious risk flags — before anything runs. Laird should show this before the *first* session on a newly added project, not just the after-the-fact cost/time footer (`observability-trust-and-harness.md`).
- **A "verify before install" gate for the plugin marketplace**, modeled on metaharness's Verify tab: check a plugin's permissions/MCP footprint and scan for embedded secrets before install, surfaced in plain language. Paired with honest disclosure wording borrowed directly from ruflo's own docs ("mods run with your account's permissions and are not sandboxed — review before installing") rather than implying a marketplace listing is automatically safe.

## Global vs. project-scoped skill visibility (resolved, implemented, and verified)

An early hardening test looked at the `system/init` event's `"skills"` list under `--setting-sources project` and concluded the flag didn't scope anything — but that list was Claude Code's own **built-in** meta-skills (`loop`, `schedule`, `doctor`, `init`, …), never the user's personal library. Workstream C re-tested against a *real* personal global skill (`~/.claude/skills/phago-status`) and got a clean, decisive result: a session started with `--setting-sources project` and asked directly whether it had that skill answered **"NO ACCESS."** So the underlying product question — should a session see the user's real global Claude Code skill library? — still needed an answer, but the flag itself already does the isolating correctly; see `architecture-and-data.md`'s corrected note.

**Resolved: neither extreme.** Full global inheritance breaks Laird's core promise for a different reason than cost — a globally-installed skill could fire unexpectedly inside a session with no visible explanation, undermining the trust/predictability pillar, and the hidden tool-advertisement token overhead (~21K tokens on a fresh session, confirmed live in Workstream A) becomes unpredictable and machine-dependent, undermining the plain-language cost promise. Full permanent isolation breaks it for the original reason — the target user already has a real Claude Code setup they've invested in, and silently hiding all of it stops feeling like "my real agent, just nicer."

**The resolution, now built and verified, not just designed**: `--setting-sources project` stays the always-on floor for every session — nothing globally installed ever applies by default. A second, clearly distinct UI section — **"Also available on this machine"** — lists every globally-installed skill/subagent/plugin, **off** by default, individually toggle-on-able per project (`src/main/skills/discovery.ts` reads the real `~/.claude/skills/`, `~/.claude/agents/`, and every enabled plugin's bundled skills via the real, free `claude plugin list --json`). Turning one on for a project is an explicit, visible, per-project choice (`Project.enabledGlobalSkillIds`), never ambient inheritance. Technically, enabling a global skill **symlinks its real directory into that session's own worktree-local `.claude/skills/`** (`src/main/skills/materialize.ts`) rather than touching `--setting-sources` at all — a project's *own* skills arrive for free, since a git worktree checks out the same tracked files as any other branch, so only global skills need this extra step. **Live-verified end to end**: with the symlink, a real session correctly quoted the exact real skill description back; without it, the identical session answered "NO ACCESS."

## This section's core decision is reaffirmed, not changed, by the research

`docs/research/external-analysis/ruvnet-github.md` examined `ruflo` (the tool whose own config is already present in this project's ambient `CLAUDE.md` files) and found it does the opposite of what's recommended here: it writes a second, parallel config system into a user's repo (`.claude-flow/`, its own `CLAUDE.md` edits, hooks, a background daemon) rather than riding on Claude Code's native plugin format. Its own README has to reassure users they "don't need to learn 314 MCP tools or 26 CLI commands" — a direct admission of the complexity failure mode Laird exists to avoid. Treat this as a concrete negative example, not a model: stay on Claude Code's native format, stay minimal.
