# Laird — Product pillars, core experience, design language

Part of the product PRD. See `docs/prd/README.md` for the full index. Read `vision.md` first.

## Product pillars

1. **Visually distinct parallel project shells.** Every project carries a consistent visual identity (color, and potentially a generated texture/icon — see design exploration) across every surface it appears on, so it is never possible to mistake which project you're acting in.
2. **Never feels like a terminal.** The underlying mechanism is a real shell/PTY running Claude Code, but the user interacts with a structured, GUI-native experience: message bubbles, collapsible file-change cards, plain-language cost/time summaries — never raw scrolling text, never character-by-character line editing.
3. **Full Claude Code feature surface, made visual.** Skills (including creating new ones), subagents, slash commands/shortcuts are all first-class, browsable, visual objects (skill cards, a skill tree/collections view, a subagent roster with live status) — not CLI-only config.
4. **Flexible multi-project navigation.** Tabs for quick switching, an optional grid ("mission control") view to see all projects at once — both are first-class, not one bolted onto the other.
5. **Finder-style file and document access.** Browse and open project files/documents the way Cursor or any modern IDE allows — without requiring the user to understand the underlying file tree as a developer would.
6. **Plugins, installed with eyes open.** Users can extend the workspace — this directly maps onto Claude Code's existing plugin/skill/MCP ecosystem (hundreds of first-party plugins, thousands of community ones) but needs a visual, browsable install experience, since today it's git-repo-and-JSON only. Every install is checked first (permissions, embedded secrets) and the workspace says plainly that installed plugins run with full account permissions, unsandboxed — never implying a false sense of safety. On adding a new project, the workspace also proposes a starter set of skills/subagents from a quick read of the project itself, instead of handing a non-engineer a blank "create a skill" form. A project never silently inherits everything already installed globally on the user's machine, either — anything installed outside Laird shows up in a separate, clearly labeled "also available on this machine" list, off by default, so turning one on for a project is always a deliberate choice, never a surprise.
7. **Harness mode.** A visual way to build and watch test/eval harnesses for agent work. A dedicated reviewer checks finished work in its own fresh context — it never did the work itself, so its verdict is trustworthy — and gives a plain verdict: **ship it, hold for review, or rework it**, against the specific criteria the user wrote in English. Integrated into the workspace itself, never a separate tool bolted on.
8. **Observability and real trust, in plain language.** Cost, time, files changed, what an agent actually did — always visible, always in a sentence a non-engineer can read, never raw tokens/traces, and always backed by a real local record of what happened (not just a description that can't be checked). Anything decorative in the interface is never mistaken for a real status. Agents can run with different levels of independence, but spending money, deleting things, or reaching the network always asks first, no matter what — and a single, always-visible control lets the user take back control from any agent immediately, with real effect, not just a setting buried in a menu.

None of these eight are optional add-ons to each other — per direction from this project's owner, they are not an either/or set; the product's differentiation is in packaging all of them into one coherent, trustworthy interface, not in picking one.

**Known gap**: pillars 1–4, 6, and 8 all have at least a sketch in the built mockups (see below). Pillar 7 (harness mode) currently has **no visual representation at all** — none of the nine design variations show where a user writes criteria or what a SHIP/HOLD/REWORK result looks like. Pillar 5 (Finder-style file access) also has only a one-line mention in the technical PRD's architecture diagram, nothing more. Both are open work, not settled.

## Core experience (from the built mockups)

- **Tab view**: a top tab bar, one tab per project, each carrying its own color/identity and live status (running / idle / N agents / needs review). The active tab's content is a structured activity stream: user messages as bubbles, agent turns labeled with the agent's identity, file changes as individual collapsible chips (file name, one-line description, diff size), a "N more steps" disclosure for the full run, never raw output. A composer at the bottom with visible slash-command shortcuts, styled as a rich input, not a prompt.
- **Grid view**: the same projects as cards in a grid — status, last message, agent-avatar stack, cost/time — for scanning everything at once and jumping in.
- **Skills & agents view**: a collections sidebar (Core skills, per-project skills, subagents, community installs) plus a card grid (icon, name, one-line description, keyboard shortcut, on/off state) and a subagent roster (identity, role, live status).
- A right-rail panel, present in the tab view, surfaces the current project's live agent activity and its most-used skills, so the full skills view is one click away but the essentials are always visible.

## Design language — locked

Nine directions were explored as full, comparable HTML mockups in `design/variations/` (see `design/README.md` for the complete writeup of each — v1 Studio Light, v2 Aurora Glass, v3 Ink & Paper, v4 Night Ops, v5 Liquid Glass Landscape, v6 Generative Seed, v7 Command Deck, v8 Big Wave). **v9 — Signature is the locked default**, converged from direct feedback across all eight:

- **Material**: v5's liquid-glass mist/paper/ink (Newsreader + Inter + JetBrains Mono), the direction most directly descended from Workspace-OS's own real shader-based glass system.
- **Identity and activation are the same control.** Every project's tab carries a real surfboard glyph (profile outline, drawn from real vector assets, not an abstract dot) in that project's color. Selecting a project's tab turns its board over — a genuine 3D flip between a side-profile "resting" view (idle) and a top-down "laid flat" view (active/running) — so the activation state and the project's visual identity are literally the same object, not a mark plus a separate switch next to it (the earlier Command Deck toggle is retired in favor of this).
- **Brand**: the surfboard mark is a deliberate reference to the project's namesake, big-wave surfer Laird Hamilton — rocker and a single fin, visible from the side.

Three rules hold regardless of future theme additions: a project is always identified by consistent color/identity, never name alone; the agent's work always renders as a structured stream, never raw text; skills and subagents always share one panel with a dedicated full view. A fourth rule was added after a later research round (see the technical PRD's `observability-trust-and-harness.md`): anything purely decorative (the mist drift, film grain, the board-flip motion itself) must stay visually distinguishable from real status — the flip's idle/active meaning and the tab's state text are signal; the atmosphere around them is not.
