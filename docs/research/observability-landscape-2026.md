# External analysis: the 2026 LLM/agent observability landscape

Scope: OpenTelemetry's GenAI semantic conventions plus the open-source LLM-observability tool landscape (Langfuse, Helicone, Arize Phoenix/OpenInference, Traceloop/OpenLLMetry, LangSmith, Braintrust), evaluated against Laird's *actual current* data model (`docs/prd/technical/architecture-and-data.md`'s Data model table; `app/src/shared/types.ts`'s `ActivityLogEntry`/`UsageEvent`/`Subagent`; `app/src/main/session/mapEvents.ts`/`sessionManager.ts`'s real `task_id` subagent correlation). Not a request to adopt any of these products — Laird's "no separate observability SaaS for v1" decision stands — this is about whether their *vocabulary* is worth aligning to now, so a future export plugin stays cheap to build, per that same PRD section's own v2+ note.

## 1. What's actually out there

- **OpenTelemetry GenAI semantic conventions** (`open-telemetry/semantic-conventions-genai`, its own repo as of 2026, still marked *Development*, not *Stable*, even for core attributes). Defines span types — `chat`, `text_completion`, `embeddings`, `generate_content`, `retrieval`, `execute_tool`, `create_agent`, `invoke_agent` — with span name format `{gen_ai.operation.name} {gen_ai.request.model}`. Only two attributes are required: `gen_ai.operation.name` and `gen_ai.provider.name` (the latter replacing the older `gen_ai.system`; values like `anthropic`, `openai`, `aws.bedrock`). Core attributes: `gen_ai.request.model`, `gen_ai.response.model`, `gen_ai.response.finish_reasons`, `gen_ai.usage.input_tokens`/`output_tokens`. Message content (`gen_ai.input.messages`/`gen_ai.output.messages`) is opt-in, not captured by default — the older `gen_ai.prompt`/`gen_ai.completion` attributes (what Traceloop's OpenLLMetry still emits) are deprecated upstream in favor of these. Agent spans (`create_agent`/`invoke_agent`, `gen_ai.agent.name`) are explicitly called out as *less settled* than the core chat/tool-call attributes as of mid-2026.
- **OpenInference** (Arize's own convention, powering Phoenix): a competing, more opinionated vocabulary — 10 span kinds (`LLM`, `EMBEDDING`, `RETRIEVER`, `RERANKER`, `TOOL`, `CHAIN`, `AGENT`, `GUARDRAIL`, `EVALUATOR`, `PROMPT`), every span required to carry `openinference.span.kind`, full message content captured by default via indexed attributes (`llm.input_messages.0.message.role`). Its own explicit three-level hierarchy — **session → trace → span** (a session is a whole conversation, a trace is one turn, spans are the steps inside that turn) — and a documented parent/child rule: a child span spawned inside an `AGENT` span auto-inherits that agent's `agent.id`.
- **Traceloop/OpenLLMetry**: builds on the `gen_ai.*` namespace but layers its own vendor-prefixed extensions on top rather than replacing it — `traceloop.span.kind` (`workflow`/`task`/`agent`/`tool`), `traceloop.workflow.name`, `traceloop.entity.name`. A real precedent for "extend the standard namespace, don't fork it."
- **Langfuse**: three observation types — `EVENT` (a discrete point-in-time marker), `SPAN` (has a duration, `end_time`), `GENERATION` (a `SPAN` specialized for one model call, carrying `model`, `usage_details` (token breakdown as JSON), `cost_details` (cost breakdown as JSON), prompt name/version links). Notably: Langfuse ships only 5 span kinds vs. Phoenix's 8 and OpenInference's full 10 — a visibly simpler, less taxonomized schema than Arize's.
- **Braintrust, LangSmith, Helicone**: eval-/CI-gate-centric (Braintrust), LangChain/LangGraph-runtime-native (LangSmith), and a lightweight proxy-based cost/cache layer (Helicone) respectively — none introduce a materially different core span vocabulary from the above; they're consumption/workflow layers over broadly the same `gen_ai.*`-adjacent shape.
- **None of these tools have an equivalent of Laird's own evidence-tier model** (`VERIFIED`/`CORROBORATED`/`UNCORROBORATED`/`INFERENCE`/`STATED`, per `observability-trust-and-harness.md`). This is genuinely not a solved problem in the mainstream observability landscape — these are *telemetry* tools (what happened, what did it cost), not *trust-tier* tools (how do I know this claim is actually true). Worth stating plainly: this isn't a gap to fill from outside, it's a real point of differentiation already designed into Laird, not found anywhere in this survey.

## 2. Adopt

- **Capture the real token breakdown `UsageEvent` currently discards.** Laird's own live-verified `claude` CLI output (confirmed earlier this project, in the Foundation workstream's own spike) already reports `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` on every real turn — `UsageEvent` today only persists `costUsd`/`durationMs`/`filesChanged`, throwing the token breakdown away. Add the four token fields to `UsageEvent`, named to match `gen_ai.usage.input_tokens`/`output_tokens` directly (a straight rename-free alignment) plus two Laird-specific `cacheReadTokens`/`cacheCreationTokens` fields (OTel GenAI doesn't yet standardize cache tokens as of 2026, so there's nothing upstream to match there). Cheap, immediately useful for the cost footer's own "how much did caching actually save me" story, and removes the single biggest reason a future OTel/Langfuse exporter would need a lossy reconstruction instead of a direct field copy.
- **Confirm, don't redesign, Laird's existing session/turn/event hierarchy against OpenInference's session→trace→span model.** Good news, not a gap: Laird's `Session` (one project tab's run) → `Turn`/`ActivityLogEntry.turnId` (one real `claude` process invocation) → individual `ActivityLogEntry` rows already maps cleanly onto session→trace→span, with no rearchitecture needed. Worth recording explicitly so a future contributor doesn't "fix" this into unnecessary complexity thinking it's unprincipled.
- **Give `Subagent` an explicit parent link, matching OpenInference's "child span inherits parent agent.id" rule.** Today a `Subagent` row is correlated to its session only by `sessionId` + the real `task_id` Claude Code assigns — there's no field recording *which* `ActivityLogEntry`/turn actually spawned it, only arrival order in the event stream. Add `Subagent.parentActivityLogEntryId` (the `ActivityLogEntry` row for the `Agent` tool-call that spawned it). This is also directly load-bearing for the harness-mode evidence-tier work from this same session's design pass: a `VERIFIED` claim backed by "a subagent checked this" needs an explicit, queryable lineage, not inferred proximity.
- **Extend `ActivityLogKind`'s small vocabulary to cleanly map onto `gen_ai.operation.name` where a real overlap exists, and keep the rest as explicit Laird extensions — Traceloop's own `traceloop.*`-prefixed-extension-over-`gen_ai.*` pattern is the right model to copy, not a wholesale vocabulary swap.** Concretely: `'tool-call'` ≈ `execute_tool`, a `Subagent` spawn ≈ `invoke_agent`, a `Turn`'s own text response ≈ `chat` — these three already have a clean standard-vocabulary home. `'kill-switch'` and `'permission-prompt'` have no OTel/OpenInference equivalent at all (they're Laird's own trust/guardrail mechanism, not a telemetry concept) and should stay exactly as Laird-specific, unprefixed today, with a `laird.`-style prefix reserved for if/when an actual OTel exporter is built — not invented now, just named as the future seam.
- **When the "export to Langfuse/OTel" plugin is eventually built, treat it as attribute translation at the export boundary, not a data-model change.** None of the above requires touching how Laird stores or renders its own data day-to-day — it's about choosing field names *now*, while the schema is still small and cheap to adjust, so that translation layer is a field-for-field copy later instead of a lossy reconstruction from a differently-shaped local store.

## 3. Don't adopt

- **The actual SaaS products, their cloud dashboards, or OTLP collector/exporter infrastructure as a live v1 dependency.** Already decided in `observability-trust-and-harness.md` ("no separate observability SaaS... for v1") — this research reaffirms, not reverses, that. OTel's wire protocol (OTLP, collectors, exporters) solves cross-service distributed tracing; Laird is one local desktop process. Only the attribute *vocabulary* is worth adopting now, never the transport.
- **Auto-instrumentation/SDK-wrapping agents** (what Traceloop's OpenLLMetry and Phoenix's instrumentors fundamentally are — monkey-patching a LangChain/OpenAI/Anthropic SDK call site to emit spans automatically). Irrelevant to Laird's actual integration shape: Laird doesn't call an LLM SDK in-process at all — it shells out to the real `claude` CLI and parses real stream-json NDJSON lines itself (`mapEvents.ts`). That NDJSON parser *is* Laird's instrumentation layer already; bolting on an auto-instrumentation library would be dead weight with nothing to instrument.
- **OpenInference's full 10-span-kind taxonomy, or Langfuse's `EVENT`/`SPAN`/`GENERATION` three-way split, as a literal replacement for `ActivityLogKind`.** Both are heavier than what Laird's actual event stream produces (Laird has no embeddings, retrieval, reranking, or guardrail *model calls* to span separately — its guardrails are deterministic, local, and already their own thing). Borrow the mapping concept (§2), not the full enum.
- **Multi-tenant cost-attribution dashboards / usage-based billing UI patterns** (Langfuse's and Braintrust's own hosted analytics). Laird is single-user, local-first; there's no "whose cost is this" question to answer, which is most of what those dashboards are for.

## 4. Open questions

- Whether `ActivityLogEntry` should grow an explicit `traceId` distinct from `turnId` once genuine multi-turn conversations (not just the current one-send-wipes-previous-turns renderer behavior, a known pre-existing gap noted earlier in this project) are actually built — today `turnId` is doing double duty as both "which turn" and "which trace," which is fine while there's only ever one live turn in view, and would need revisiting the moment that changes.
- Whether to literally timestamp a `gen_ai.provider.name`-shaped field now (`"anthropic"`) even though Laird is explicitly single-provider for v1 — low cost either way, but adding it now costs nothing and removes one more future migration if/when the provider question ever reopens (not a recommendation to reopen it — see the already-settled single-provider non-goal).
- Whether the `laird.*` extension-attribute prefix (for kill-switch/permission-tier/evidence-tier data with no standard-vocabulary home) should be decided now or really can wait until the export plugin is actually being built — leaning toward "wait," since naming it prematurely risks guessing wrong about what the export boundary actually needs, and nothing today reads that prefix either way.
