# External research: AI-agent / coding-agent eval-harness landscape (2026)

Scope: how the field builds harnesses that check an AI agent's work — eval frameworks, LLM-as-judge reliability, deterministic coding-agent verification (SWE-bench), and visual/UI verification. Grounded against Laird's own harness-mode design in `docs/prd/technical/observability-trust-and-harness.md` and the three live findings added there this session (screenshot evidence, Playwright-MCP click-through, the embedded-PiP proposal).

## 1. The single most important finding: `claude plugin eval` is a real, working harness Laird should wrap, not reinvent

Confirmed live on this machine (`claude plugin eval --help`). It is a genuine eval-harness mechanism built into Claude Code itself, with a case format (`case.yaml` or `prompt.md` + `graders/*.md`), and architectural features more mature than anything currently in Laird's own harness-mode draft:

- **Multiple runs per case, by default** (`--runs`, default 3) — treats a single LLM-graded run as unreliable on its own and requires repeated sampling before trusting a score. Laird's harness-mode draft currently implies one reviewer run per criterion; this is a real, concrete gap.
- **Ablation** (`--ablation with-without`, the default whenever a plugin resolves): runs a no-plugin baseline arm and reports the *score delta* — isolating "did this pass because of the agent's work" from "would this have passed anyway." Directly transferable to Laird: a harness criterion's `VERIFIED` tag is far stronger if it's a delta against a pre-change baseline, not just a post-hoc check.
- **Mocks for MCP servers** (`--mocks record`, default): a dependency with no mock simply isn't started, keeping most runs fast/deterministic/free; real servers only start with explicit `--allow-real-servers` opt-in. Mirrors the same "explicit opt-in, never ambient" discipline already in Laird's own skill/MCP materialization design.
- **Cost ceiling** (`--max-cost-usd`) and **threshold-based CI exit codes** (`--threshold`, default 1.0) — a harness run can be bounded and gated the same way a CI pipeline gates on a build.
- **Judge model is explicitly separate and overridable** (`--judge-model`, defaults to haiku) — the grading model is already treated as a distinct, swappable role from whatever model did the work, not implicitly the same model.
- **Self-contained HTML report** with per-grader verdicts, optionally published to claude.ai — a real precedent for what a harness-run *results view* (Workstream G's own flagged design gap) could look like, without Laird inventing a report format from scratch.

This is scoped to evaluating a **plugin's own prompt-triggering behavior**, not "does this project satisfy a human-written acceptance criterion" — so Laird can't literally invoke `claude plugin eval` against a project. But every one of the mechanisms above (multi-run aggregation, ablation, mock-first/real-opt-in, cost ceiling, separate judge model, HTML report) is a direct, concrete answer to gaps in Laird's current harness-mode draft, and reusing the *shape* keeps Laird consistent with its own stated philosophy of never reinventing a Claude Code mechanism that already exists.

## 2. LLM-as-judge pitfalls and mitigations — directly relevant to the shortcut-taking failure already found live

The 2026 consensus (DeepEval's own field guide, multiple practitioner surveys) names the same failure modes Laird already hit in its own live testing this session: **position bias, verbosity bias, and self-preference** — plus, closest to Laird's actual finding, judges that take a cheaper path to an answer instead of genuinely checking. Named mitigations, in order of how directly they transfer:

- **A different judge model than the agent, at minimum a different size, ideally a different provider** — "using the judge and the agent from the same model family introduces correlated error: the judge shares the same blind spots as the agent." Laird's reviewer is explicitly fresh-context (good) but nothing in the current design requires it to be a *different model* than whatever built the work. Laird's single-provider-v1 non-goal rules out a different provider, but a different model size (e.g., build with Sonnet, review with Opus, or vice versa) is fully compatible with that constraint and should be an explicit harness-mode setting, not left implicit.
- **Aggregation across multiple calls, not a single run** — matches `claude plugin eval`'s own `--runs` default directly (§1 above); independent confirmation this is a real, field-standard practice, not over-engineering.
- **Binary scoring and swapped positions in pairwise comparisons** — less directly applicable to Laird (criteria are single-sided SHIP/HOLD/REWORK judgments, not pairwise comparisons between two candidates), but binary-first scoring (does this specific, narrow sub-claim hold, yes/no) before any aggregate disposition is a good discipline to carry into how a numbered criterion decomposes into checks.
- **Calibration against a small hand-graded set — named as "the largest source of error, and the practice most teams under-invest in."** Laird has no equivalent today and should treat this honestly as a real limitation to disclose, not solve by assumption: a harness's `VERIFIED` tag is only as trustworthy as whatever hand-checking ever validated the reviewer's own judgment, and right now that number is zero.

DeepEval specifically scores **agent trajectories**, not just end states, via named metrics — `TaskCompletionMetric`, `StepEfficiencyMetric`, `PlanAdherenceMetric`, `PlanQualityMetric`. Laird's own `ActivityLogEntry` log already contains everything needed to compute equivalents (did the agent touch the files it claimed to, how many turns/tool-calls did it take, did it follow a stated plan) — worth treating as a concrete shape for criteria that are about *how* the agent worked, not just whether the final state looks right.

## 3. SWE-bench's deterministic pattern — and its own 2026 cautionary tale

The real mechanism: hand the agent a repo + an issue; the agent emits a unified diff; the harness applies the patch and runs the **project's own real test suite** in a sandboxed container; "resolved" means the previously-failing tests now pass *and* the previously-passing tests still pass. This is the fully machine-checkable end of the spectrum Laird's harness-mode draft already flags as an open question (deterministic sub-checks vs. LLM judgment) — and it's a strong, concrete answer for any Laird criterion that reduces to "the tests should pass": run the project's actual test command and query the exit code, no LLM judgment needed at all.

**The cautionary tale, found live in the same research pass**: OpenAI's own Frontier Evals team stopped reporting SWE-bench scores in February 2026 after an internal audit found that more than 60% of a sampled set of "resolved" tasks were actually unsolvable as written, because the underlying tests were flawed. The lesson transfers directly and uncomfortably well to Laird: a harness is only as good as the criteria/tests it's checking against, and Laird's own criteria are written in plain language *by a non-engineer user* — a strictly harder authoring problem than SWE-bench's own (which still got 60% wrong with professional maintainers writing the tests). **Concrete addition this motivates**: Laird's harness needs a step that can flag a criterion itself as ambiguous or unverifiable, separate from flagging the agent's work as failing — "I can't tell what this means well enough to check it" has to be a real, surfaced outcome, not something the reviewer silently guesses past.

## 4. Visual regression testing: baseline-diffing is the industry default, not zero-shot LLM judgment — and a "record once, replay deterministically" pattern is available

Percy (Review Agent + AI-powered diff), Chromatic (YIQ `diffThreshold`), and Playwright's own built-in comparison (`pixelmatch` + YIQ threshold) are all **baseline-diff** tools first: they compare a new screenshot against a previously *accepted* screenshot, and use AI/perceptual-diff math only to separate a real visual regression (broken layout, wrong color) from noise (anti-aliasing, subpixel rendering, font hinting) — not to judge a screenshot cold, from scratch, the way Laird's current design (hand a screenshot to the reviewer, ask if it satisfies a plain-language criterion) does. This is an important, direct correction to make before implementation: **zero-shot LLM visual judgment and baseline-diffing are different tools for different criteria shapes.** "The button should still look the way it did before this change" is a baseline-diff question (cheap, deterministic, no LLM needed at all once a baseline exists). "The signup form should look professional on mobile" is a genuinely novel qualitative judgment with no baseline to diff against, and is the real, narrower case where an LLM visual judge (or the click-through/embedded-PiP approach already designed this session) actually earns its cost.

Separately, Playwright's own 2026 "Test Agents" feature ships a **planner → generator → healer** pipeline: a planner writes a test plan from a prompt, a generator turns it into a real Playwright test script, and a healer re-runs and repairs that script over time as the page changes. This suggests a genuinely valuable pattern for Laird's own click-through harness evidence (already designed this session, live-verified against the real Playwright MCP plugin): **the first harness run against a UI-shaped criterion is LLM-driven and exploratory (clicking around, reading state) — but its successful run can be saved as a real, reusable Playwright script.** Every *subsequent* harness run against that same criterion replays the saved script directly — fast, free, fully deterministic — and only falls back to the LLM-driven exploratory path if the saved script breaks (the project's UI changed shape). This turns a one-off, costly, somewhat-unreliable LLM judgment into a durable regression check after the first pass, directly addressing the cost/reliability tension the PRD's own "machine-checkable sub-checks vs. LLM judgment" open question already names.

## Adopt

- **Borrow `claude plugin eval`'s mechanisms directly into Laird's own harness-run implementation**: multi-run aggregation per criterion (not a single reviewer pass), an ablation-style baseline comparison where feasible, mock-first/real-opt-in for anything MCP-dependent, a cost ceiling per run, a separate/overridable judge model from whatever built the work, and a self-contained HTML-style results report as the concrete shape for the still-undesigned results view.
- **Require the reviewer to be a different model (at minimum a different size) than the builder**, as an explicit harness-mode setting — cheap, compatible with the single-provider non-goal, and a direct, field-validated mitigation against correlated-blind-spot judging.
- **Add an explicit "criterion unverifiable/ambiguous" outcome**, distinct from a failing disposition on the agent's work — directly motivated by SWE-bench's own 2026 audit finding that the majority of a "resolved" set's failures were bad tests, not bad agents.
- **Split UI-shaped criteria into baseline-diff checks (deterministic, cheap, for "did this break") versus LLM-judged checks (for genuinely novel/qualitative criteria with no baseline)** — don't route every visual criterion through an LLM judge by default.
- **Record-once-replay-deterministically for click-through evidence**: save a successful LLM-driven exploratory browser session as a reusable Playwright script; replay it on subsequent runs; only re-invoke the LLM path when the saved script actually breaks.
- **Treat DeepEval's agent-trajectory metric categories (task completion, step efficiency, plan adherence, plan quality) as a vocabulary for criteria about *how* the agent worked**, computable from Laird's own existing `ActivityLogEntry` log without adopting the library itself.

## Don't adopt

- **Any hosted/cloud eval SaaS as a v1 dependency** (Braintrust's hosted UI, Percy/Chromatic's cloud diff services) — consistent with Laird's already-stated local-first, no-cloud-dependency-for-v1 non-goal; their *mechanisms* are worth borrowing, their hosted products are not worth depending on.
- **Pairwise/swapped-position judging** — Laird's criteria are single-sided SHIP/HOLD/REWORK judgments, not A/B comparisons between two candidate outputs; this specific bias-mitigation technique doesn't map onto Laird's actual judgment shape.
- **A literal integration with `claude plugin eval` itself** — it evaluates a plugin's own prompt-triggering, not a project's acceptance criteria; the right move is reusing its *mechanisms*, not calling the subcommand against a project.

## Open questions

- No real calibration process exists yet (in the field broadly, or in Laird's own design) for validating that a reviewer's `VERIFIED` judgments are actually trustworthy over time — named by the field as the most under-invested mitigation, and genuinely unsolved here too.
- Exactly how "a different model size for the judge" should be surfaced as a user-facing setting (automatic default vs. explicit per-project choice) is undecided — a product decision, not just a technical one.
- Whether Laird should build its own pixelmatch-based local baseline-diff mechanism now, or defer it until a concrete criterion shape demands it — the embedded-PiP/click-through design already approved this session covers the LLM-judged half; the deterministic-diff half of the split recommended above has no owner yet.
