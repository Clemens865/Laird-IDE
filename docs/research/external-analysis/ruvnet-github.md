# External analysis: github.com/ruvnet

Scope: survey of ruvnet's GitHub profile, evaluated against Laird's current product/technical PRDs and the locked v9-signature design direction. Not a full audit of all ~50 public repos — focused on the ones actually relevant to an agent-orchestration desktop IDE.

## 1. What the surveyed repos actually are

- **`ruflo`** (74,028 stars, TypeScript) — this IS "claude-flow," renamed. Confirmed directly in its own README ("Claude Flow is now Ruflo"). This is the exact tool whose config (swarm/hive-mind topology, SPARC methodology, 98 agents, memory/hooks instructions) is already present in this project's own `CLAUDE.md` files, inherited from global and project-level setup — it is real, existing, actively maintained tooling (12.5M npm downloads/12mo), not hallucinated noise. It installs as either a lightweight Claude Code plugin (slash commands only) or a full CLI (`npx ruflo init`) that writes `.claude/`, `.claude-flow/`, `CLAUDE.md`, hooks, and a background daemon into a project. Its core pitch: "Agent = Model + Harness" — it's the execution layer around Claude Code/Codex adding specialized agents, swarm coordination, persistent/learning memory, and a visual "console" (a separate cockpit UI showing workflows, agents, tokens, cost, logs, replay).
- **`metaharness`** (688 stars, TypeScript) — one of the 4 projects this analysis round was explicitly asked to cover. Not a harness *runner* — a harness *generator*: `npx metaharness <repo>` scaffolds a brand-new, repo-specific CLI + MCP server + agent set + memory namespace + governance policy, output as an npm package the user owns and brands. Its own words: "It is not another agent framework. It is a factory for agent frameworks." This is a different sense of "harness" than Laird's product-PRD pillar (which means: plain-language acceptance criteria checked against an agent's work, i.e. an eval/test harness for one project) — important not to conflate the two when reworking the PRD.
- **`RuVector`** (4,541 stars, Rust) — a vector/graph DB built for agent memory: local vector search, persistent context, graph relationships, feedback/contrastive learning, positioned as the memory backend under both `ruflo` and `metaharness`.
- **`open-claude-code`** (512 stars, JS) — a clean-room, decompile-informed rebuild of the actual Claude Code CLI: "async generator agent loop, 25 tools, 4 MCP transports, 6 permission modes, hooks, settings chain, sessions." Built via another of the author's own tools (`ruDevolution`, an AI-assisted decompiler). MIT-licensed, but explicitly built from "decompiled source intelligence" of Anthropic's proprietary CLI.
- **`agentic-flow`** (816 stars) — a provider-routing shim in front of Claude Code/Agent SDK, for swapping in cheaper models and deploying agents to the cloud.
- Everything else scanned (RuView — 96.7k★ WiFi/RF sensing, `dream-machine`, `autogenous`, `rudevolution`, `rGi`, `QuDAG`, `ruqu`, `rvcsi`, `worldgraph`, etc.) is either unrelated hardware/sensing/quantum work or self-modifying-software research with no bearing on a coding workspace.

## 2. Adopt

- **Tiered autonomy + mandatory confirmation + a visible kill switch (from ruflo's console).** Concretely specified in their own docs: permission levels `read` / `write` / `manage` / `full`, crossed with `ask` / `auto` approval; network, spending, and destructive actions require confirmation *even in `auto`*; a live action log; a one-click **"Take back control"** that immediately revokes agent autonomy and causes the next action to be refused. This is a more concrete, already-battle-tested version of Laird's still-vague trust/guardrail layer (product PRD pillar 8, technical PRD §9 security). **Recommendation: adopt this exact shape** — tiered permission × approval mode, hard-coded exceptions for spend/destructive/network actions regardless of tier, an always-visible log, and a literal kill switch in the UI.
- **Read-only, pre-session "report card" (from metaharness's `score`/`analyze-repo`).** `npx metaharness score <repo>` reads a repo (never executes it) and prints a one-screen fit/safety/cost estimate before anything is scaffolded. **Adopt a lightweight version**: when a user adds a new project to Laird, show a quick, non-destructive "here's what I found" summary (stack, size, obvious risk flags) before the first agent session starts — cheap to build, directly reinforces the trust pillar, and gives a new non-engineer user a soft landing instead of an empty activity stream.
- **Honest disclosure language for unsandboxed extensions.** Ruflo's docs plainly state mods "run with your account's permissions and are not sandboxed... review the code before installing" rather than implying a plugin marketplace is automatically safe. **Adopt the wording pattern**, not a mechanism: Laird's plugin-marketplace browser (product PRD pillar 6) should carry the same plain disclosure, not a false sense of safety.
- **"Agent = Model + Harness"** is a clean one-line framing worth borrowing for Laird's own docs/onboarding copy — it cleanly explains *why* a visual workspace around Claude Code adds value, independent of any specific implementation.

## 3. Don't adopt

- **Ruflo's own scale is a cautionary tale, not a model.** Its README has to reassure users "you don't need to learn 314 MCP tools or 26 CLI commands" — that is an admission of the exact failure mode Laird exists to avoid. Do not adopt its breadth (98 agents, 60+ commands, 30 skills, a daemon) as an aspiration; if anything, treat "314 tools" as a negative benchmark when scoping Laird's own skill/subagent surface.
- **Invasive, parallel install footprint.** The CLI path writes `.claude-flow/`, its own `CLAUDE.md` edits, hooks, and a background daemon into a user's repo — a second, parallel config system sitting next to Claude Code's own. This directly contradicts Laird's technical PRD §5 decision to ride on Claude Code's *existing* plugin/skill format rather than invent a new one. **Confirms, don't changes, Laird's existing decision** — explicitly do not replicate Ruflo's pattern of a separate harness config layer.
- **Federation / multi-machine swarms.** Out of scope per Laird's own v1 non-goals (local-first, not a cloud/multi-provider platform). Plausible v2+ idea at most, not now.
- **MetaHarness's self-modifying "Darwin Mode"** ("the harness mutates its own config... keeps only what measurably improves") and its cryptographic witness-chain/governance machinery. Both are wrong fits for Laird's actual audience: a trust-first product for non-engineers should never have the workspace silently rewriting its own behavior, and enterprise-grade signed-provenance release gates are far beyond v1 scope. Keep the underlying *intent* (don't blindly trust agent output — verify it, per Laird's existing "Reviewer" subagent / harness-mode concept) without any of this mechanism.
- **`open-claude-code` as a dependency.** Reading it to understand Claude Code's real internal shape (agent loop, 6 permission modes, hooks, settings chain, sessions) is useful *background research* for de-risking Laird's single biggest open technical question (§11 of the technical PRD: the real SDK/headless integration surface). But it is a decompiled, clean-room rebuild of Anthropic's proprietary CLI — depending on, bundling, or shipping any of its code in a commercial product built on a healthy relationship with Claude Code/Anthropic is a real legal/reputational risk. **Read for understanding only; do not depend on or vendor it.**
- **Model-routing (`agentic-flow`, `@metaharness/router`).** Reasonable idea in isolation, but conflicts with Laird's explicit v1 non-goal of staying Claude-Code-first/single-provider. Not now.

## 4. Open questions

- Whether `open-claude-code`'s documented internals (25 tools, 4 MCP transports, 6 permission modes) actually match the *current* real Claude Code CLI/SDK closely enough to be useful even as reference material — it's nightly-synced to upstream releases per its own README, but its accuracy wasn't independently verified here.
- Whether any of Ruflo's "console" (the separate cockpit UI) was built against Claude Code's structured/SDK event stream or against raw terminal output — if the former, its source could be a faster way to validate Laird's core technical bet (§3 of the technical PRD) than a from-scratch spike. Worth a follow-up look specifically at `plugins/ruflo-console` if this question matters enough to chase.

## 5. Re-checked: should a Laird user be able to "activate Ruflo" from the UI?

Asked directly during Workstream C, after Laird had real architecture to check this against (session isolation, hook/MCP neutering, and the native `SubagentRoster` built in chunk 4) — a different question than §2/§3 above, which was about borrowing *ideas*, not literally integrating the real tool.

**Rejected.** Concrete conflicts, not hypothetical:
- Ruflo's background daemon spawns its own headless `claude` sessions on an interval and consumes tokens continuously (confirmed in this very project's own ambient CLAUDE.md) — invisible to Laird's `UsageEvent`/`ActivityLogEntry` model, which only captures what `SessionManager` itself spawns. A user could be billed by a process Laird's own cost footer never shows — directly breaks the plain-language-cost trust pillar.
- Every real session Laird starts forces `disableAllHooks`, an empty `--mcp-config --strict-mcp-config`, and `--setting-sources project`. Ruflo's hooks/MCP server would be silently neutered the moment a Laird session ran, unless Laird carved out a deliberate exception — which would reopen the exact global-skill-visibility security work done in Workstream C chunk 3/4.
- No daemon-free path exists: Ruflo's console (the one genuinely useful feature) requires the full invasive install; there's no lightweight, hooks-free, visualization-only mode.
- Reliability risk observed live, not assumed: this exact project's own `claude-flow` MCP server is configured but failing to connect (`CONNECTION_CLOSED`) on this machine, right now.
- **What Laird already has without any of this**: `SubagentRoster.tsx` (Workstream C chunk 4), sourced directly from Claude Code's own real `task_*` system events when the main agent spawns a subagent via the native `Agent` tool — live, zero extra config, fully inside Laird's own cost/activity model. This answers §4's open question above: the market's own answer converged on exactly this "native, no daemon" shape — Anthropic shipped a first-party `claude agents` dashboard (Agent View) directly in Claude Code in 2026, which validates Laird's approach rather than suggesting Ruflo's console as a better integration target. (Standalone community alternatives like Claudia/ClauBoard exist but are apps in Laird's own category, not libraries to embed.)

**Still worth keeping**: only the already-adopted *idea* from §2 — tiered permission × approval mode plus a visible kill switch — which is Workstream D's job, not a Ruflo dependency.

## Most important finding

Ruflo's "Claude control" feature — tiered permission levels crossed with ask/auto approval, hard exceptions for spend/destructive/network actions, a live action log, and a one-click "take back control" kill switch — is the single most directly reusable idea found anywhere in this survey. It's a concrete, already-shipped answer to the exact trust/guardrail problem Laird's PRD currently leaves as an open pillar with no real mechanism behind it, and it should be lifted (the *shape* of the feature, not any code) into Laird's technical PRD §9 and product PRD pillar 8 in the upcoming rework.
